PHANTOM(1) General Commands Manual PHANTOM(1)

NAME

phantom - record real HTTP traffic, replay it against a new build, answer every third-party call from the recording

replay production traffic
against your next build.
stripe never finds out.

Phantom sits in front of your service and beside its outbound calls, and records both sides of every request. Later it fires those requests at a staging build, serves the third-party responses from disk, and tells you what changed: which JSON paths drifted, and which outbound calls were added, dropped or made twice.

$ 
git clone https://github.com/sepehrmohseni/phantom && cd phantom && make setup && make
[setup guide] [cloud waitlist]
you@laptop: ~/shop

This is a simulated shell with a small shop service in it, so you can try the whole flow without installing anything. The story plays first. Then the prompt is yours: click the terminal and type help, or press tab to complete commands. The recording and the replay both return 201. The double charge only shows up as outbound drift.

WHY YOU MIGHT NEED THIS

Most backend bugs that reach production aren't crashes. A field changes type. A call happens twice. A retry turns out not to be idempotent. A provider sends back a response nobody handled.

Unit tests miss these because they mock the provider with whatever the author expected it to return. Staging misses them because nobody sends staging the requests real users send. You hear about it from a support ticket, or from Stripe.

Phantom treats the traffic you already have as the test suite. Every captured request is a test case, and its third-party calls become fixtures you never had to write.

where it pays off
  • + refactoring billing, checkout, signup, anything that talks to payment, email or SMS providers
  • + framework, ORM or language upgrades on a service whose tests you don't fully trust
  • + rewrites and migrations, where the new service has to answer exactly like the old one
  • + bumping a provider SDK and wanting to see every request that changed shape
  • + reproducing a production bug locally from the exact request that caused it
  • + inheriting a legacy service and finding out what it actually does on the wire
where it doesn't
  • - services with no outbound calls and good tests. A plain diff of responses, or no tool at all, is fine
  • - streaming and websocket heavy apps. Phantom buffers whole HTTP bodies
  • - load testing. Replays are sequential on purpose, one session at a time
  • - anything that can't be pointed at a proxy for its third-party calls

SYNOPSIS

phantom start  [--upstream URL] [--inbound-port 8080] [--outbound-port 8081] [--ui-port 9000]
               [--db-path FILE] [--ignore-field JSONPATH]... [--capture-queue N]
               [--bind 127.0.0.1] [--ui-bind 127.0.0.1]

phantom replay [--api URL] [--target URL] [--session ID]... [--json]

GETTING STARTED

About ten minutes, most of it compiling. Fill in your own addresses and every command below follows along.

your setupnothing leaves this page
  1. 1. build it

    Needs a Rust toolchain. make setup adds the wasm target and installs trunk, which builds the console. Plain cargo build also works if you don't care about the console.

    git clone https://github.com/sepehrmohseni/phantom && cd phantom
make setup
make
sudo install target/release/phantom /usr/local/bin/
  2. 2. start it in front of your service

    Phantom forwards everything on :8080 to your service and records it. Your service doesn't need to know yet. Everything binds to 127.0.0.1 by default; add --bind 0.0.0.0 when traffic comes from other machines, and keep :8081 off anything public, since it will proxy to wherever it's asked.

HOW A REPLAY IS JUDGED

        

          
signature

          
SHA-256 over method, host, path, sorted query and the body with its keys sorted. Key order and whitespace don't matter; values do.

          
matching

          
Exact signature first. Then method and path, for bodies that carry nonces or idempotency keys, picking the closest unused recording so parallel calls don't get crossed. Then a call that was already used once, which is how retries and double charges stay visible instead of failing with a miss.

          
body diff

          
Recursive JSON diff with paths like $.items[2].status. 100 and 100.0 are equal. Form-encoded bodies are compared field by field as well, and switching between JSON and form is a type mismatch. Anything else is compared as text, or as hex if it isn't UTF-8.

          
drift

          
Extra calls, missing calls, and request bodies that changed under a fallback match are reported next to the body diff. Any of them fails the run, even when the status code and the response look fine.

          
storage

          
redb: one file, ACID. A single writer batches up to 512 sessions per commit behind a bounded queue. If the disk can't keep up, captures are dropped and counted. Live requests never wait on storage.

          
secrets

          
Authorization, cookie and API-key headers on outbound calls are replaced with [redacted] before anything is written. Bodies are stored as they are.

          
console

          
j k to move, r to replay, : for commands, ? for the rest. It's compiled into the binary.

        

      


      

        
DIAGNOSTICS

        

          
502 phantom_sandbox_miss

          
The new build made a call the recording never saw. That's usually a real finding, a new dependency. If it isn't, record again with the current code.

          
sessions have 0 outbound calls

          
The calls aren't reaching :8081, or they arrive without x-phantom-trace-id while other requests are in flight. Check the header is copied from the incoming request.

          
HTTPS_PROXY does nothing

          
HTTPS through a proxy is a CONNECT tunnel, and phantom doesn't intercept TLS. Use the x-phantom-target-url header or the base-url form shown in step 3.

          
every replay fails on one field

          
It's noise. Replay against the recording build, collect the paths that drift, and pass them to --ignore-field.

          
dropped_sessions > 0

          
The disk fell behind a burst and captures were shed to keep requests fast. Raise --capture-queue or record a sample.

          
403 from the control plane

          
It only answers to localhost, and refuses cross-origin browser requests. Start it with --ui-bind 0.0.0.0 to reach it from other hosts, or --cors-origin for a page on another origin.

          
no replay target given

          
In record mode phantom will not guess where to replay, because the default upstream is often production. Pass --target, or switch to sandbox mode with a staging url.

          
exit status 2

          
The replay couldn't run: the control plane is unreachable, the session id matches nothing, or the target build is down. The message says which.

at least one session drifted

the replay could not run: unknown id, control plane unreachable, or the target is down

        

      


      

        
PHANTOM CLOUD

        

          

            The open source binary is the whole engine, and it stays that way. Cloud is for teams who want it running against every pull request without looking after a redb file on some box.
          

          
    
            
  • + capture storage with retention and sampling, one catalogue per service
    • 
            
  • + PII and card data tokenised at the edge before it leaves your network, consistently, so diffs still line up
    • 
            
  • + a GitHub Actions check that replays a slice of real traffic against each preview deploy and blocks the merge on drift
    • 
            
  • + pass rate, latency delta and new third-party dependencies across all your services in one place
